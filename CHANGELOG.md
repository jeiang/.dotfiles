# Changelog

## Unreleased

### Added

- `modules/packages/hypr-rdp.nix` + `modules/hosts/artemis/default.nix`: hypr-rdp (github.com/MuNeNICK/hypr-rdp), a native RDP server for Hyprland, packaged here and added to artemis' `environment.systemPackages` so the session is reachable from an RDP client over the NetBird mesh. Not run from upstream's own flake for two reasons: its `cargoHash` is stale, so `nix run github:MuNeNICK/hypr-rdp#hypr-rdp` fails outright on a fixed-output hash mismatch against the vendor derivation, and building against upstream's pinned nixpkgs gave a libva that did not match artemis' Mesa -- `radeonsi_drv_video.so` loaded with "no function __vaDriverInit_1_0" and the session silently dropped to software H.264. Built against this flake's nixpkgs instead, which also means a different `cargo vendor` result than upstream's package.nix declares (`syn` vs `syn 2.0.117` in the vendored lock), hence a third distinct `cargoHash` here. A `postPatch` widens hypr-rdp's Hyprland-IPC fallback: it sizes its headless output with `keyword monitor <rule>` and only falls back to `eval hl.monitor{...}` when the refusal says "keyword can't work with non-legacy parsers", but Hyprland 0.56's Lua config parser answers `keyword` with a bare "unknown request", so start-up died with "failed to set headless output resolution" before the server ever listened. `modules/nixos/hyprland/hyprland.lua` gains the matching `screencopy` permission grant, same unattended-host reasoning as the existing sunshine one -- the regex is `.*hypr-rdp.*` rather than sunshine's `.*/bin/sunshine` because Hyprland matches on the client's `/proc/<pid>/exe` and this package wraps its binary, so the real path is `.../bin/.hypr-rdp-wrapped`. Run by hand, not as a unit: it takes credentials on the command line, so a service would need a secret first.
- `modules/hosts/artemis/default.nix`: declare `services.avahi.enable = true` on artemis. avahi was only up as a transitive `mkDefault` from the nixpkgs `sunshine` module, and the ESP32 HomeKit Wake-on-LAN Switch's Probe resolves `artemis.local` over mDNS before pinging it -- so dropping or reworking sunshine would have broken the Switch silently. `openFirewall` stays at its default.
- `docs/adr/0012-extend-the-scoped-credential-agent-into-a-tiered-fleet-operator.md`: records the three-tier fleet-operator model (free/soft-confirm/forbidden, enforced by the `hermes-ops` sudo allowlist), the private-network SSH transport decision, and the new credential inventory (Actual Budget, iCloud CalDAV, a second GitHub PAT, Grafana annotations) for the upcoming Hermes fleet-operator expansion. `CONTEXT.md` gains "Fleet Operations Tiers" and "hermes-ops" glossary entries; `docs/runbooks/hermes.md` gains skeleton "Credential inventory and rotation" and "Verifying the operations tiers" sections.
- `modules/nixos/hermes-ops/default.nix`: the fleet-wide `hermes-ops` unprivileged user and its per-node sudo allowlist (ADR 0012's Fleet Operations Tiers classifier), wired onto all four Legion nodes by `modules/hosts/legion/default.nix`. Sudoers, not doas: Legion enables `security.sudo` fleet-wide and never imports `modules/nixos/security.nix`'s doas module (artemis-only) -- an earlier doas-based draft of this allowlist evaluated but never actually ran on Legion, since no doas binary exists there; the option surface and per-tier data model are unchanged, only the rendering mechanism. Each node declares its tier-1/tier-2 systemd unit lists as data; `systemctl start`/`restart` NOPASSWD `sudo` rules are generated per unit (identical for both tiers -- the confirm gate is prompt-level), `systemctl stop` for every listed unit, and `netbird status`/a single-purpose `netbird expose` wrapper (verified against the pinned netbird 0.76.1 CLI). `hermes-ops` is the only sudo user on every node, node3 included -- `hermesOps.journalGrantees` (renamed from `extraGrantees`: the sudo grant that name implied never worked, since the upstream `hermes-agent` unit's `NoNewPrivileges=yes` blocks any in-process privilege escalation regardless of sudoers) grants legion-node3's `hermes` service user `systemd-journal` membership only, not sudo. `docs/runbooks/hermes.md`'s "Verifying the operations tiers" section is filled in with exact commands.
- `modules/nixos/hermes/default.nix`: the Hermes-side half of ADR 0012's `hermes-ops` fleet-execution transport -- a new `hermes/ssh-key` sops secret installed (overwrite-on-start) to `${stateDir}/.ssh/id_ed25519`, plus a Nix-managed `${stateDir}/.ssh/config` with per-node `Host` blocks for every Legion node, node3 included -- the upstream `hermes-agent` unit's `NoNewPrivileges=yes` blocks any in-process privilege escalation, so even node3's own privileged actions have to cross an sshd boundary like every other node's (no committed Legion SSH host keys exist to pin against, so host-key verification uses `StrictHostKeyChecking accept-new` against a persistent `known_hosts`, documented tradeoff in-module and in the runbook) and `pkgs.openssh` added to `extraPackages`. Also declares `settings.memory.nudge_interval = 10` and `settings.skills.external_dirs` pointing at the Knowledge Base clone's `skills/` (both verified against `cli-config.yaml.example` at the pinned hermes-agent rev). `SOUL.md` gains the fleet-operations tier policy and a much stronger knowledge-discipline section (write during conversations, Obsidian-vault conventions, a starting folder taxonomy); `SERVERS.md` gains the exact per-node tier table, sudo invocation forms, expanded VictoriaLogs LogsQL examples with real journald field names, the journalctl fallback, and `netbird expose`'s foreground/backgrounding and stop/list mechanics (verified against the pinned netbird 0.76.1 source -- no list/stop subcommand exists). `docs/runbooks/hermes.md`'s credential-inventory entry for the SSH key is filled in with the concrete secret name, install path, and host-key-verification note.
- `modules/packages/actual-cli.nix`: a standalone Nix packaging of the official `@actual-app/cli` npm package (verified as the exact CLI the `actual-budget-import` skill targets) via `buildNpmPackage` against a synthetic single-dependency lockfile (`modules/packages/actual-cli/`) -- npm resolves `@actual-app/api`'s `workspace:*` dependency to its published registry version for an external install, avoiding the upstream yarn-workspace monorepo's own build toolchain entirely. `better-sqlite3`'s native install script builds fully offline via `buildNpmPackage`'s own `node-gyp`-against-Nix-headers path.
- `modules/nixos/hermes/default.nix`: five personal-service integrations for the Hermes fleet-operator (docs/adr/0012). **Actual Budget** (feature 3): the new `actual-cli` package added to `extraPackages`, `ACTUAL_SERVER_URL` set directly (non-secret), `ACTUAL_SESSION_TOKEN`/`ACTUAL_SYNC_ID` folded into the existing `hermes/env` sops secret. **iCloud Calendar** (feature 8): `khal`/`vdirsyncer` added to `extraPackages`, a Nix-rendered vdirsyncer config (single-sided `collections = ["from b"]` to keep `discover` non-interactive) referenced directly from the Nix store via `VDIRSYNCER_CONFIG`, a Nix-managed khal config installed to its default path by preStart, and a new `hermes-vdirsyncer-sync` oneshot+timer (15m cadence, mirrors `hermes-kb-sync`'s shape) using `ICLOUD_USERNAME`/`ICLOUD_APP_PASSWORD` (also folded into `hermes/env`) via vdirsyncer's `password.fetch`/`username.fetch` "command" strategy. **artemis LLM provider** (feature 7): a `settings.providers.artemis` custom OpenAI-compatible entry pointed at llama-swap's raw NetBird peer IP (not the mesh DNS name, for reachability when the mesh itself is degraded), no credential, a 600s `request_timeout_seconds` for cold model loads, and verified never reachable through the automatic fallback chain (`hermes_cli/fallback_config.py` reads only `fallback_providers`/`fallback_model`, neither touched here) -- manual `/model`/`--provider` switch only. **Other Git repos** (feature 9): `HERMES_REPOS_TOKEN` (folded into `hermes/env`) for the agent's own interactive `gh`/`git` against four repos beyond the Knowledge Base, used explicitly per-command so the existing `GITHUB_TOKEN`/`hermes-kb-sync` path is unaffected -- no new sync unit, deliberate-commit discipline per ADR 0012. **Grafana annotations**: `GRAFANA_URL` set directly (non-secret, loopback) and `GRAFANA_ANNOTATION_TOKEN` (folded into `hermes/env`) for the agent's own `curl` POSTs to `/api/annotations`. No new `sops.secrets` entries -- all six new credential/config values fold into the existing `hermes/env` secret. `SOUL.md` gains an expanded "GitHub access" section (two tokens, used explicitly) and a "Calendar" note; `SERVERS.md` gains "Budget (Actual)", "Calendar", "Alternative model (artemis)", "Other Git repos", and "Grafana annotations" sections; `docs/runbooks/hermes.md`'s credential-inventory entries are filled in with exact secret line names, mint/rotate steps, and consumption points, plus a consolidated pre-deploy `hermes/env` checklist.

- `modules/nixos/hermes/default.nix`: makes Hermes proactive. Enables the upstream webhook platform (`platforms.webhook`, loopback-bound on `127.0.0.1:8644`, verified against the pinned hermes-agent rev to run inside the same already-running `hermes gateway` process -- no new unit, port change, or dependency needed, `aiohttp` already ships via the "all" dependency-groups build) with a Nix-declared `alertmanager` route: no route script, just a `prompt` template that turns the raw Alertmanager payload into an investigate-and-report brief and `deliver: "telegram"` for automatic delivery of the agent's final response. The route is deliberately investigate-and-report ONLY -- the prompt forbids any `systemctl`/`netbird expose`/`sudo` action from that turn, deferring remediation to Aidan's approval in the normal Telegram conversation; `platform_toolsets.webhook` still grants `["terminal"]` (overriding the upstream default, a narrow toolset meant for untrusted third-party webhook content) since read-only investigation (VictoriaLogs/VictoriaMetrics/`systemctl status`/journalctl) needs it and none of those reads touch sudo or cross-node SSH. This is a prompt-level, not mechanical, boundary -- ADR 0012 gains a paragraph naming the webhook as a distinct lower-trust injection surface (alert content vs. Aidan's own Telegram input) alongside its existing "Tier 2's soft enforcement is a residual risk, accepted" section, with the sudo allowlist remaining the actual backstop. `modules/nixos/monitoring/default.nix`'s `discord-notifications` Alertmanager receiver gains a second `webhook_configs` notifier pointed at the loopback endpoint (one receiver, both notifier types -- simpler than a `continue: true` routing tree) alongside the existing `discord_configs`, so every alert still reaches Discord too. No new secret: the adapter's own `INSECURE_NO_AUTH` escape hatch is scoped to loopback binds, which this is. Cron scheduling needed no wiring at all -- verified the `cronjob` toolset is already available to Telegram-driven sessions (the "CLI-only" note in `cli-config.yaml.example`'s toolset-list comment is stale; `check_cronjob_requirements()` explicitly gates on `HERMES_GATEWAY_SESSION` too) and the gateway process already runs an in-process cron ticker, so routines are seeded through conversation rather than Nix. `SOUL.md`/`SERVERS.md` gain sections on both capabilities; `docs/runbooks/hermes.md` gains synthetic-alert verification (`curl`/`amtool`, expecting a diagnosis-and-recommendation message, not an autonomous fix) and cron-routine inspection steps.

### Fixed

- `modules/nixos/hyprland/default.nix`: artemis' wallpaper actually paints again. hyprpaper 0.8 replaced the old `preload = <path>` + `wallpaper = <monitor>,<path>` pair with a `wallpaper {}` special category (`src/config/ConfigManager.cpp`: keys `monitor`/`path`/`fit_mode`/`timeout`/`order`/`recursive`; `preload` no longer exists at all). The old form is not rejected, just ignored -- hyprpaper started clean, logged "Monitor DP-1 has no target: no wp will be created", and left an unpainted white desktop, which is also what any screen-sharing client saw. Rewritten as the block form with an empty `monitor` (matches every output) and `fit_mode = cover`. Worth knowing for the next hypr* bump: hyprpaper has not moved to Lua (hyprwm/hyprpaper#366 is still open), so this stays a hyprlang file even though `hyprland.lua` is not.
- Prepend the nix-darwin profile paths (`~/.nix-profile/bin`, `/etc/profiles/per-user/$USER/bin`, `/run/current-system/sw/bin`, `/nix/var/nix/profiles/default/bin`) in the wrapped fish's darwin config -- macOS login shells start from `path_helper`'s PATH, so `environment.systemPackages` tools (first symptom: `direnv hook fish` at startup) were unreachable. Linux config text is unchanged.
- Add the operator account to `users.knownUsers` (uid 501) on zakkart so the wrapped-fish login shell actually applies -- nix-darwin only writes `UserShell` for known users, so the previous bare `users.users.<name>.shell` was silently ignored and the account stayed on `/bin/zsh`.
- Declare `trusted: true` on every Brewfile tap entry so Homebrew >= 6.0's tap-trust enforcement doesn't refuse to load formulae/casks from the pinned third-party taps (`netbirdio/tap`, `can1357/tap`, `k06a/tap`) during activation.
- Move the host toolbox out of the wrapped Fish shell and use Cachix's pinned binary package to avoid IFD evaluation.
- Replace the pinned-store-path Cachix package (`builtins.storePath`, impure) with nixpkgs' `pkgs.cachix` — the pinned paths were old Hydra builds of the same 1.11.1 `-bin` output already cached on cache.nixos.org — and drop `--impure` from CI now that nothing violates pure evaluation.
- Export `DIRENV_CONFIG` in the wrapped fish's darwin login shells -- the wrapped fish never sourced nix-darwin's `set-environment`, so nix-direnv's loader (`/etc/direnv/direnvrc`) never loaded and `use flake` silently fell back to direnv's builtin, uncached implementation, re-evaluating dev shells on every prompt.
- `modules/nixos/hermes/SOUL.md`: stop Hermes duplicating its own skills into the Knowledge Base. The knowledge-discipline section described `knowledge-base/skills/` as "a backup of skills you've created", while `settings.skills.external_dirs` already loads that same directory as a live skill source -- so every skill existed twice under one name, and upstream's ambiguity check (`tools/skills_tool.py`, pinned rev: "Ambiguous skill name ... Refusing to guess") rejected the bare name for *both* copies, not just the duplicate. The section now describes the KB as where those skills *live*: `skills create` still writes to `~/.hermes/skills/` first (upstream has no configurable write target -- issue #4381 is closed as completed but `default_write_dir` exists nowhere in the tree, at the pinned rev or at HEAD), and the skill is `git mv`d from there into `knowledge-base/skills/<category>/` with no copy left behind. Bundled skills stay in `~/.hermes/skills/` under `skills_sync.py`'s manifest, explicitly never mirrored into the KB. External dirs remain read-only for *autonomous lifecycle maintenance* only (`agent/skill_utils.py` `is_external_skill_path`) -- foreground edits still work, and category resolution reads relative to the external root (`_get_category_from_path`), so a KB skill keeps a real category rather than collapsing to one. Deliberately not solved with a symlink: `tools/skill_manager_tool.py` `_find_skill` walks with `Path.rglob`, which does not descend into symlinked directories, so `skill_manage` would have gone blind to every KB skill (upstream PRs #75225/#67748 fix this, both still unmerged).
- `modules/nixos/hermes/default.nix`: `hermes-vdirsyncer-sync` now answers `discover`'s collection-creation prompt instead of dying on it. With auth fixed, the first successful discovery listed the four iCloud calendars and then blocked on `Should vdirsyncer attempt to create it? [y/N]` for each local counterpart -- a systemd oneshot has no stdin, so the unit failed on the prompt rather than on the sync. The in-module comment claiming `collections = ["from b"]` kept discovery non-interactive was wrong: that setting decides which side is authoritative, not whether missing local collections are created. `discover` has no `--yes` (only `--list`, verified against vdirsyncer 0.20.0's own `--help`), so the answer is fed on stdin. Bounded `printf 'y\n'`x100 rather than `yes |`: under the script's `set -euo pipefail`, a `yes` killed by SIGPIPE when vdirsyncer exits first would fail the unit, while ~200 bytes fits the pipe buffer and always exits 0. Answering `y` is the intent, not a rubber stamp -- the local vdir is Disposable State mirrored from iCloud, so there is no local-only calendar a `y` could clobber.
- `modules/nixos/hermes/default.nix`: scheduled routines no longer die with a node rebuild. Upstream stores them in `get_hermes_home()/cron/jobs.json` -- Disposable State under `stateDir`, with nothing backing it up -- so every `cronjob`-created routine was silently lost on rebuild despite `SERVERS.md` presenting them as durable. `hermes-agent`'s preStart now symlinks that store into the Knowledge Base clone (`.hermes-cron/`, dot-prefixed so Obsidian hides it while `git add -A` still commits it), which makes the existing `hermes-kb-sync` timer push it and a rebuild restore it with the clone -- durability without a Hetzner Volume, so `stateful = false` in `modules/hosts/legion/_service-inventory.nix` stays correct. A `! -L`-guarded one-time migration moves a pre-symlink real directory across first; without it `ln -sfn` would link *inside* the existing directory and orphan the routines in it. `hermes-kb-sync`'s bootstrap changes from `git clone` to `git init`+`fetch`+`checkout -f` as a consequence: the preStart creates a path inside the clone directory, and `git clone` refuses a non-empty destination -- on a fresh node the agent's preStart wins that race whenever it starts before the timer's first run. `docs/runbooks/hermes.md` gains the symlink verification and drops the implied post-rebuild re-creation step.
